## Topic 1: The Event Loop

The **event loop** is the mechanism that lets single-threaded JavaScript handle async work without blocking. It coordinates the **call stack**, the **microtask queue** (Promises, `queueMicrotask`), and the **macrotask queue** (`setTimeout`, `setInterval`, I/O).

```js
console.log("1: sync");

setTimeout(() => console.log("2: timeout (macrotask)"), 0);

Promise.resolve().then(() => console.log("3: promise (microtask)"));

console.log("4: sync");

// Output:
// 1: sync
// 4: sync
// 3: promise (microtask)
// 2: timeout (macrotask)
```

**Key Points:**
- Synchronous code runs first, fully draining the call stack.
- After the stack is empty, **all microtasks** run before the next macrotask.
- `Promise.then`/`catch`/`finally` and `await` continuations are microtasks.
- `setTimeout(fn, 0)` does **not** run immediately — it waits for the current stack and all pending microtasks to finish.
- A flood of microtasks can starve macrotasks (e.g. an infinite microtask loop blocks rendering).

## Topic 2: Debouncing & Throttling

Both limit how often a function runs in response to rapid events (typing, scrolling, resizing) — but they behave differently.

```js
// DEBOUNCE: run only after activity has stopped for `delay` ms
function debounce(fn, delay) {
  let timer;
  return function (...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), delay);
  };
}

// THROTTLE: run at most once every `limit` ms
function throttle(fn, limit) {
  let waiting = false;
  return function (...args) {
    if (waiting) return;
    fn.apply(this, args);
    waiting = true;
    setTimeout(() => (waiting = false), limit);
  };
}

// Usage
const onSearch = debounce((e) => console.log("search:", e), 300);
const onScroll = throttle(() => console.log("scroll tick"), 200);
```

**Key Points:**
- **Debounce** = "wait until it's quiet." Good for search inputs, autosave, resize-end.
- **Throttle** = "at a steady rate." Good for scroll handlers, mouse-move, infinite scroll.
- Both rely on **closures** to keep `timer`/`waiting` state between calls.
- Use `fn.apply(this, args)` so the original `this` and arguments are preserved.

## Topic 3: Currying & Partial Application

**Currying** transforms a function of many arguments into a chain of functions that each take one argument. **Partial application** fixes some arguments up front and returns a function expecting the rest.

```js
// Normal function
const add = (a, b, c) => a + b + c;

// Curried version
const curriedAdd = (a) => (b) => (c) => a + b + c;
console.log(curriedAdd(1)(2)(3)); // 6

// Partial application
function multiply(a, b) {
  return a * b;
}
const double = multiply.bind(null, 2); // fix a = 2
console.log(double(5)); // 10

// A simple generic curry helper
function curry(fn) {
  return function curried(...args) {
    if (args.length >= fn.length) return fn.apply(this, args);
    return (...next) => curried.apply(this, [...args, ...next]);
  };
}
const sum = curry((a, b, c) => a + b + c);
console.log(sum(1)(2)(3));   // 6
console.log(sum(1, 2)(3));   // 6
console.log(sum(1)(2, 3));   // 6
```

**Key Points:**
- Currying always takes **one argument at a time**; partial application can fix **several** at once.
- Both build on **closures** (the inner function remembers earlier arguments).
- `fn.length` tells you how many parameters the original function declared — useful for a generic `curry`.
- Great for creating reusable, configured helpers (e.g. `const log = curry(...)`) and for function composition.
